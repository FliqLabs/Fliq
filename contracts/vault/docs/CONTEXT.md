# FLIQ contract context

- The vault holds users' USDC on NEAR, keeps balances, only releases USDC for orders registered by the backend, limits what AI agents can spend, and records verifiable receipts. It does not compare rates, convert money or send bank transfers. A USDC transfer to the provider is NOT proof that bank money arrived.
- CONFIRMED public method names, in this argument order: `register_order(order_id, payer, deposit_address, amount, expiry, corridor)`, `payout(order_id, amount, deposit_address)`, `release_order(order_id)`, `transfer(to_account, amount)`, `set_payout_timeout(payout_timeout)`, `resolve_stuck_payout(order_id, transferred)`, `set_status(order_id, status, refs)`, `recredit(order_id, amount)`, `get_receipt(order_id)`, `get_balance(account)`. CONFIRMED event names: `order_registered`, `payout_executed`, `order_released`, `status_set`, `deposited`, `recredited`, and `transferred`.
- Amounts are integer base units, never floats, strings in JSON.
- Two status tracks: the vault `transfer_state` (`Registered`, `Executing`, `Dispatched`, `Released`) is verified on NEAR; a failed transfer returns to `Registered` for retry. The backend status is only a report. Backend statuses: `created`, `awaiting_deposit`, `deposit_seen`, `routing`, `with_provider`, `paying_out`, `settled`, `refunding`, `refunded`, `provider_timeout`, `awaiting_recon`, `expired`, `failed`, `refused`, `not_received`.
- OPEN items, never treated as decided and always kept behind one clearly named placeholder with a comment starting `OPEN:`: order ID mapping, corridor encoding, provider allowlists, relayed-agent identity, daily limits, order/receipt storage cleanup, and deployment accounts.
- Safety rules: credit only real token receipts, never send an order twice, change state BEFORE creating the transfer promise, restore funds if the transfer fails, a stale callback changes nothing, backend calls can never move value on their own, no personal data in events or receipts.
